# Vibe coding 赋能推理优化

> 一句话：推理优化里最贵的从来不是想法，是**照着硬件把代码重写一遍**的人力。AI 写代码正从两个层次啃掉这块成本——**算子级**（MusaCoder：PyTorch 算子 → 原生 Kernel）与**系统级**（VibeServe：直接生成整套 serving 栈）；两者共同的底气是这类任务**自带可自动判定的正确性与性能**。

## 零、为什么这件事在推理优化上特别成立

推理优化的成本结构很特殊：**算法层的点子基本是公开的，贵的是把它落到具体硬件上的工程量**。[[国产GPU与NPU适配]] §一 把这件事说得很直白——CUDA 生态里最难替的不是驱动、也不是算子库，而是**上层那一堆照着 CUDA 手写的推理库**：「芯片能跑矩阵乘不难，难的是几十个手写 CUDA kernel 的推理库要一个个重来」。

这正是 vibe coding 的靶心。而且比起业务代码，这里有一个决定性的有利条件：

> **这类任务自带裁判。** 算子有 PyTorch 参考实现可做数值比对，系统有压测可量吞吐与延迟——**正确性和性能都能自动判定**，生成出来的东西不需要人逐行读懂才敢用。下面两个工作的核心机制里都摆着这个「裁判」。

按生成粒度分两级：

| 层次 | 代表 | 生成什么 | 替掉的人力 | 成熟度 |
|---|---|---|---|---|
| **算子级** | **MusaCoder**（摩尔线程） | 单个 Kernel（PyTorch → CUDA/MUSA） | 手写与调优 kernel | 已发布、权重开源 |
| **系统级** | **VibeServe**（arXiv 2605.06068） | 整套 serving 栈 | 通用系统的长期打磨 | 论文阶段 |

## 一、算子级：MusaCoder

### 1.1 是什么

2026 年 6 月 10 日，摩尔线程正式发布并开源 **MusaCoder**——面向 GPU 底层**算子生成**的专用代码大模型：

| 项 | 内容 |
|---|---|
| **参数规模** | **9B** 与 **27B** 两档 |
| **能力** | 从 PyTorch 标准算子**自动生成高性能 CUDA / MUSA 原生 Kernel 代码** |
| **评测** | KernelBench 上 MusaCoder-27B-RL 取得 **Overall Pass@8 93.2%**、**Avg.@8 88.60%** |
| **训练** | 完整后训练流程在基于 **MTT S5000** 构建的**夸娥智算集群**上完成 |
| **开放** | 模型权重已开源 |

摩尔线程自己也用 MusaCoder 这类 AI 工具做了技术实践。

> 「后训练全程跑在自家 S5000 集群上」这句本身也是个信号：**训练侧自证 + 生成侧补算子**，是同一套自研栈的两头。



### 1.2 为什么是摩尔线程做这个

放回国产卡的上下文，这一步的位置就清楚了。按 [[国产GPU与NPU适配]] §五，摩尔线程在 SGLang 里走的是**「重编译 CUDA 代码」而非「重写实现」**的路线：MUSA 的 API 与 CUDA 高度相似，算子默认回退到 `forward_cuda`，同时它在 `sgl-kernel` 里备了一整套独立的 C++ 编译链（`setup_musa.py`、`csrc/musa/`）。

两块拼图正好互补：

| 拼图 | 解决什么 | 出处 |
|---|---|---|
| `sgl-kernel/csrc/musa/` 编译链 | **能编** —— CUDA 源码几乎不改就能落到 MUSA | [[国产GPU与NPU适配]] §五 |
| **MusaCoder** | **谁来写** —— 剩下那些编不过、或需要重调的 kernel 交给模型生成 | 本节 |

对照昇腾：[[国产GPU与NPU适配]] §4.3 记了它的文档里有**两篇专门的「算子开发与调优」指南**——这恰恰说明**算子开发是硬件适配里最占人力的一环**。一家「写指南教人写」，一家「训个模型替人写」，是同一道题的两种解法。

## 二、系统级：VibeServe

> **VibeServe: Can AI Agents Build Bespoke LLM Serving Systems?**
> arXiv **2605.06068**（2026-05-07，cs.AI / cs.DC）｜Keisuke Kamahori、Shihang Li、Simon Peter、Baris Kasikci
> 代码：`github.com/uw-syfi/vibe-serve`（org 名 `uw-syfi` 指向华盛顿大学）

### 2.1 论点：通用性是被成本逼出来的

以前因为人工写代码太贵，我们被迫用「万能但平庸」的通用系统；现在有了 AI 自动写代码，我们可以**低成本地为每一个具体的任务（模型 + 硬件 + 场景）自动生成一个「量身定制、极致高效」的专用系统**，从而打破性能瓶颈。

论文开篇的说法与此完全一致：多年来 serving 系统都被当作关键基础设施来建——**「一个通用栈，靠许多 engineer-year 手工调优，指望它支持所有模型和所有 workload」**。VibeServe 押的是反向的一注，作者自己的总结是一句很好用的话：

> **generation-time specialization rather than runtime generality**
> —— 用「生成时定制」取代「运行时通用」。

**关键在于成本结构变了，而不是技术突然可行了。** 专用系统一直都更快，只是过去每一个「模型 × 硬件 × 场景」组合都要配一支团队来写、来养，账算不过来。

### 2.2 怎么做：外循环 + 内循环

VibeServe 自称是**第一个端到端生成完整 serving 栈的 agentic loop**，双层结构：

| 循环 | 职责 |
|---|---|
| **外循环（outer loop）** | 在**系统设计空间**里做搜索：规划候选方案、跟踪搜索进展 |
| **内循环（inner loop）** | 把候选**实现出来**、**验正确性**、并在**目标 benchmark 上实测性能** |

内循环这三件事就是 §零 说的那个「裁判」：**正确性 + 实测性能构成搜索的适应度函数**，外循环才有东西可爬。**没有可自动判定的目标，这套 loop 立刻退化成瞎猜。**

### 2.3 结论：标准场景打平，非标场景才赢

论文结果分两半，**这两半必须一起读**：

| 场景 | 结果 |
|---|---|
| **标准部署**（现有栈已被高度优化） | **与 vLLM 打平** —— 原文措辞是「remains competitive」，用来说明**生成时定制不以性能为代价** |
| **非标场景**（共 6 个） | **超过现有系统**，靠的是抓住通用系统抓不到的机会：**非标准模型架构、workload 先验知识、硬件特定优化** |
