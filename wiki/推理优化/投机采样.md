# 投机采样（Speculative Decoding）

> decode 阶段搬一次权重只产出 1 个 token，算力大量闲置。投机采样用**便宜的方式先猜 γ 个 token，再让大模型一次 forward 并行验证**——把闲置的算力换成吞吐。本篇按**草稿是怎么产生的**分三大类整理：草稿模型 / 辅助层 / 数据匹配。

## 零、共同骨架

不管哪条路线，一轮投机都是同样三步，区别只在**第 1 步怎么产草稿**：

| 步骤 | 做什么 |
|---|---|
| **draft（猜）** | 产出 γ 个候选 token |
| **verify（验）** | 把 γ 个草稿拼成一条序列送进 target，配特制 attention mask，**一次 forward** 拿到所有位置的 logits |
| **accept（收）** | 逐位比对，从第一个不匹配处截断；前面的保留，后面的连同 KV 一起丢弃 |

**为什么划算**：verify 那次 forward 搬的权重字节数，和「只吐 1 个 token」的那次**完全相同**，产出却可能是 α+1 个 token。

**「+1」是白送的**：验证最后一个被接受的草稿时，target 在该位置输出的 logits 本身就是**下一个** token 的预测。所以**哪怕 γ 个草稿全被拒，这一步也至少产出 1 个 token**，不会空转。

> 三大类的分野，一句话：**草稿模型**类另起一个模型去猜；**辅助层**类让 target 自己多长几个头去猜；**数据匹配**类干脆不用模型，从历史文本里查出来。越往后 draft 成本越低，但适用面越窄。

## 一、草稿模型：给大模型配一个 draft model

草稿模型负责生成、大模型（target）负责验证。

1. 用一个更小的 **draft model（草稿模型）**按常规自回归方式先「猜」出接下来 **γ 个 token**；
2. 再让原始的大模型（Original LLM）对这串猜测进行**验证**，验证只需要**一次 forward**。

如果草稿模型在这 γ 个 token 里有 **α 个猜对了**，那么原始大模型的一次 forward 就等价于「确认」了 α 个 token，并且还能再生成**下一个 token**，也就是**一次 forward 产出 α+1 个 token**，从而达到加速效果。

**这条路线的两个先天问题**：

- 在这个框架里，**草稿模型和原始大模型做的是同一件事**——给定当前 token 序列，预测下一个 token。想用一个**参数规模小很多**的模型把这件事做好非常困难，往往导致效果不理想（命中率不够高、收益被稀释）。
- 草稿模型是**独立预测**，并没有利用原始大模型在推理过程中已经抽取出来的、非常丰富的语义信息，这也会带来潜在的效率损失。

> 第二点正是下一节所有方法的出发点：**既然 target 前向时已经算出了高质量的上下文表征，为什么要让 draft 从零猜？**Medusa / EAGLE / MTP / DFlash 都是在回答这一个问题，区别只在「用 target 的哪一层、以什么方式喂给 draft」。
>
> 另：draft 与 target 必须**同词表**，否则草稿 token 无法直接送进 target 验证。

## 二、辅助层：在 target 上加头，让它一次多吐几个

在大模型基础上增加一些头层，使其能生成更多的字符，如 Medusa、EAGLE、MTP 等。

### 2.1 Medusa

- 首先生成各个位置的候选 token；Medusa 通过接在原模型上的**多个解码头**来获取多个位置的候选 token；
- 把各个位置的候选 token 进行处理，选出一些候选序列，进行验证；Medusa 通过 **tree attention** 来处理；
- 最后通过 **typical acceptance** 选择最终输出的结果。

![[specdec-medusa-heads.png]]

> 几个头是**彼此独立**地预测各自位置的，头与头之间没有依赖——这是 Medusa 相对 EAGLE 的主要弱点，也是后面 DFlash 遇到的同一个问题（见 §2.6、§2.7）。

### 2.2 EAGLE-1：复用 target 的倒数第二层特征

核心思路是**直接利用原始大模型已经计算出来的上下文特征（contextual features）**。具体来说，在原始模型预测下一个 token 的过程中，会自然产生倒数第二层（second-top layer）的输出特征向量——这些特征**不需要额外计算**，可以直接拿来用。

EAGLE 的 draft model 由三块组成：**Embedding layer、LM Head、Autoregression Head**。其中 Embedding layer 和 LM Head **直接复用 target LLM 参数，不需要训练**；训练的主要是 Autoregression Head。

流程：

1. 在原始大模型执行一次 forward 的过程中，收集它倒数第二层输出的特征向量，构成**特征序列** `(bs, seq_len, hidden_dim)`；并结合这次 forward 由原始 LLM 生成的一个 token，构成 **shifted token 序列** `(bs, seq_len)`；
2. 将以上两者作为输入：特征序列 `(bs, seq_len, hidden_dim)` + shifted token 序列 `(bs, seq_len)`；
3. 将 shifted token → embedding，然后与 feature 拼接成 `(bs, seq_len, 2×hidden_dim)`；
4. 以这些特征为起点，**FeatExtrapolator（特征外推器）**进入「猜测（guessing）」阶段；
5. FeatExtrapolator 以自回归方式预测下一个特征向量，随后用原始模型中**冻结的 LM head** 得到 token 的概率分布，并从该分布中采样生成 token。

![[specdec-eagle1-feat-extrapolator.png]]

通过多次重复「预测特征 → LM head 得到 token 分布 → 采样 token」的过程，可以形成一种**树状（tree-like）**的生成过程：

![[specdec-eagle1-draft-tree.png]]

在图中的示例里，FeatExtrapolator 只用了 **3 次 forward**，就「猜」出了一个包含 **10 个 token** 的树状候选序列。

> **为什么在特征空间外推、而不是直接猜 token**：token 是采样出来的离散量、天然带不确定性，特征是连续的、且承载了 target 的「意图」，比 token 序列更规律、更好预测。

### 2.3 EAGLE-2

主要改进是把「**固定形状的静态 draft tree**」换成「**基于上下文动态调整的 draft tree**」，并取得了比 EAGLE-1 快 20% 以上的效果。
**核心观察：draft 的置信度 ≈ token 的接受率（“校准良好”）**

### 2.4 EAGLE-3

**直接移除 L_fea 损失**，让 draft 不再必须拟合 target 的 top-layer feature，而是更直接地服务于「猜 token」，从而释放模型容量，让「加数据」真正能转化为更高的 Step 1 接受率。

![[specdec-eagle3-multilayer-fusion.png]]

> 配图画的是 EAGLE-3 的**多层特征融合**：不再只取倒数第二层，而是把低/中/高层的特征一起喂给 draft。这和「移除 L_fea」是一体两面——不必拟合某一层特定的 feature 了，才谈得上自由地融合多层。
> 为了解决上面这种“训练-推理不一致 / 多步误差累积”，EAGLE-3 引入 **training-time test**：训练时不再只训练 Step 1，而是**在训练过程中显式执行“测试时会发生的步骤”。**如下图所示：

### 2.5 MTP（Multi-Token Prediction）

将大模型原始的 1-token 生成，转变成 **multi-token 生成**，从而提升训练和推理的性能。具体来说：

- **训练阶段**：一次生成多个后续 token，可以一次学习多个后续位置上的 label，进而有效提升样本的利用效率、提升训练速度；
- **推理阶段**：通过一次生成多个后续 token，实现成倍的推理加速来提升推理性能。

![[specdec-mtp-modules.png]]

> MTP 的优势是**官方 checkpoint 自带、和主模型一起训过**，接受率极高。代价是只有原厂放出 MTP 头的模型（如 DeepSeek 系）才能用。
>
> 落到框架里，**MTP 走的是 EAGLE 的代码路径**——[[LLM分布式]] §8.4 有 SGLang 侧的核对：`--speculative-algorithm NEXTN` 只是 `EAGLE` 的别名。

### 2.6 DFlash：把 target 特征注入 draft 的 K/V

![[specdec-dflash-arch.png]]

**1) 特征融合（Feature Fusion）**

在 **prefill**（首次前向、建立上下文）或 **verification**（目标模型验证草稿）之后，从**目标模型（target）**中提取隐藏层特征（hidden features），并对这些特征进行融合处理（fuse）。

直观理解：目标模型刚算完一轮，它内部「已经理解了上下文并形成了高质量表征」，DFlash 直接把这份「理解」提取出来作为草稿生成的强条件信息。

**2) 条件注入（Conditioning）**

这些融合后的特征会被**直接送入草稿模型各层的 Key/Value 投影（K, V projections）**里，并缓存到草稿模型的 **KV cache** 中。这句话非常关键：

- 不是简单把特征拼到输入 embedding 上；
- 而是更「注意力机制友好」的注入方式：直接影响 draft 模型注意力的 K/V（也就是「它该关注什么、如何组织上下文信息」）；
- 这样 draft 在生成时就能以目标模型的表征为「导航」。

**3) 并行起草（Parallel Drafting）**

在上述「富上下文条件」（rich context）以及**最后一个已验证 token** 的条件约束下，草稿模型用**扩散方式并行预测下一段 token block**（比如一次预测一个 block）。可以理解为：

- 自回归 drafter：下一 token、再下一 token……**串行**写草稿；
- DFlash drafter：**一次性把「下一段」草稿并行写出来**，然后交给 target 去验收。

**4) 降低开销的工程策略（Minimize overhead）**

为了把额外开销压到最低，DFlash 做了两个很实用的设计：

1. 草稿模型**复用**目标模型的 **embedding 层**和 **LM head（输出头）**——embedding 是把 token 映射到向量空间的那层，LM head 是把隐状态映射回词表 logits 的那层。这样能省参数、减显存，也减少训练/部署复杂度。
2. **只训练中间层（intermediate layers）**。也就是说，draft 模型主要学的是「怎么在注入了 target 特征后，快速把中间表征变成可用的下一段 token 分布」。

作者最终把 draft 的层数设为 **5 层**，理由是在「草稿质量（接受率）」和「生成速度（drafter 成本）」之间取折中。

> **DFlash 与 EAGLE 的分野**：EAGLE 是**自回归**地一个个外推特征，DFlash 是**扩散式**一次并行吐一整块。前者天然带序列依赖，后者快但块内各位置彼此独立——这正是 §2.7 DSpark 和 §2.8 DFlash 2 要补的洞。

### 2.7 DSpark：给 DFlash 补上块内序列依赖

DFlash 的问题是**缺少序列感知能力**。DSpark 的做法：**保留 DFlash Backbone 不变，仅通过两个轻量级辅助模块，补齐其最薄弱的序列依赖环节**。整个模型仍维持一次 forward 完成块级预测的能力，仅在输出 draft logits 之前新增两个模块。

![[specdec-dspark-pipeline.png]]

**模块一：Markov Logit-Bias Head** —— 利用前一个 token 修正当前预测。

采用**一阶马尔可夫假设**：预测当前位置 k 的 token，只需要考虑**前一个位置的 token x_{k−1}**，而忽略更早的历史信息。这大大简化了问题。

![[specdec-dspark-markov-head-bias-formula.png|545]]

- **输入**：前一个 token 的索引 x_{k−1}。
- **W₁（Embedding Lookup Table）**：大小为 `V × r` 的矩阵，V 是词表大小，r 是一个较小的维度（文中默认为 **256**）。通过查找操作 `W₁[x_{k−1}]` 取出与前一个 token 对应的嵌入向量，得到一个 r 维向量——相当于把离散的 token ID 转换成连续的稠密向量表示。
- **W₂（Logit Projection）**：大小为 `r × V` 的矩阵，把上一步的 r 维向量投影回 V 维空间。
- **B(x_{k−1}, ·)（Transition Bias）**：最终输出一个长度为 V 的向量，每个元素可看作对应下一个可能 token 的「偏好分数」或「偏置项」。这个向量会被**加到模型的原始 logits 上**，从而影响最终的预测概率。

**RNN head（Markov head 的替代方案）**：维护循环状态 s_k，累积块内**完整前缀历史**。通过门控更新整合前一状态、前一 token 嵌入和 backbone 隐藏状态。在长块上略优于 Markov head，但实现更复杂。

![[specdec-dspark-rnn-head-input-formula.png|408]]
![[specdec-dspark-rnn-head-gated-update-formula.png|612]]

**模块二：Confidence Head** —— 预估每个 draft token 被接受的概率。

对每个 draft 位置 k 输出一个标量估计，表示「给定前面所有 token 已被接受的前提下，当前位置 token 通过验证的**条件概率**」。

![[specdec-dspark-confidence-head-formula.png]]
- `W₁` 是一个线性变换矩阵，把前一个 token embedding 映射到与 hₖ 相同维度。
- 然后和 hₖ 拼接在一起 → 形成一个新的特征向量，同时包含“当前上下文信息” + “前一个 token 的影响”。
- 用当前隐藏状态 hₖ 和前一个 token 的嵌入经过线性变换后的结果，输入到一个二分类器（sigmoid + 权重向量），预测“当前 token 是否会被 target 接受”的概率。

训练用 **L1 loss的变体**：L1 距离最大值为 2（当两个分布完全对立时），除以 2 后范围变成 `[0, 1]`，方便后续计算。**越相似 loss 越小**。

![[specdec-dspark-confidence-target-l1-formula.png]]

这两个模块带来的**额外计算开销极低**，却能显著提升整体接受率。

> Confidence Head 的产物不只是一个诊断指标——它是**调度用的**：知道每个位置多大概率会被接受，就能决定这一块草稿验到第几个位置为止、多余的算力该分给谁。[[LLM分布式]] §8.4 提到 SGLang 侧对应的是 ragged-verify 调度器和那张离线 profile 出来的 SPS 代价表。

### 2.8 DFlash 2（2026-08-18）：Keep Drafting Parallel

![[specdec-dflash2-arch.png|700]]

**问题 1：块内预测互不相干。** DFlash 并行地**独立**预测每个位置，每个预测本身都合理，但它们之间**缺乏逻辑联系**，因此在验证阶段，不连贯的预测块会被截断。

![[specdec-dflash2-vs-dflash-selection-cycle.png]]

**分析 1：正确答案其实就在候选集里，只是没排到第一。** DFlash 的首选词准确率高达 **85.4%**，但正确的词条有 **99.5%** 的概率出现在其**前 16 个候选**中。即使首选词条错误，正确的词条通常也在列表里。

![[specdec-dflash2-recall-top1-vs-top16.png]]

如果有一个预测系统总能从前 16 名候选里选出最合适的，那么**接受长度将从 4.27 增加到 6.79**。

**解决方案 1：并行路径选择器（Parallel Path Selector）。**

1. 每个位置保留 **top-16** token；
2. **评估相邻位置候选 token 的兼容性**；
3. 从候选空间中选出一条**连贯路径**。

![[specdec-dflash2-path-score-formula.png]]

- `U_t(b)`：原始 DFlash 对候选 b 给出的 logit；
- `A(a)`：前一个 token 的低维 embedding；
- `B(b)`：当前 token 的低维 embedding；
- `H(h_t)`：由当前位置 hidden state 产生的**上下文门控**。

> 打分只看**相邻**两个位置（一阶），所以整条路径的最优解可以并行求出，不必真的枚举 16^k 条路径——这是它能叫「parallel path selector」的关键。配图右侧标的 "all adjacent pairs scored at once → one path kept" 说的就是这件事。

**问题 2：后缀衰减（suffix decay）。** 上表的召回率在区块末尾均有所下降：即使选择完美，准确率仍会从第一个位置的 **99.5%** 降到最后一个位置的 **87.8%**。**任何选择器都无法解决这个问题**，因为候选集本身的质量也在变差。

**分析 2：** 五层主干网络可能太小，无法维护块内各位置之间的依赖关系。但是增加深度会带来参数量上涨，而且会在 block 前部也增加计算——**前部本来就没有太大问题**。

![[specdec-dflash2-depth-ablation-recall.png]]

> 这张图是上面这段判断的依据：把 DFlash 从 3 层加到 5 层、再加到 15 层（参数量增加 3 倍），末端召回确实在涨，**但「5 层 + 转换器」（仅 +3% 参数）就基本追平了 15 层**。所以问题不在「容量不够」，而在「缺一个专管块内依赖的部件」。

**解决方案 2：two-tap dynamic depthwise conv。** block 越靠后的位置越不准，DFlash 2 给出的解释是：**attention 分配给 block 内部依赖的比例随层数快速衰减**——Layer 1 有 30%，到 Layer 5 只剩 8%。深层 attention 都跑去看长上下文了，block 内部「后面几个 token 该怎么接前面几个」这件事没人管。所以设计一个专门的模块来处理块内的工作。

![[specdec-dflash2-intra-block-attn-heatmap.png]]

在每个 attention 和 MLP **前后**插入 **two-tap dynamic depthwise conv**。「dynamic」指卷积系数不是纯静态的——由一个学到的 base kernel，加上一个从当前 hidden state 算出的 correction 组成，且**每 16 个 channel 共享一个 correction**（这是参数量能压住的关键）。

![[specdec-dflash2-two-tap-dynamic-conv.png]]
![[specdec-dflash2-two-tap-conv-formula.png]]

**为什么只看前一个位置就够**：最紧的依赖就在相邻之间，不用搜远的；而且层层堆叠之后，**感受野自然会扩张**。

卷积系数的三点小结：

- 包含一个**学习得到的基础 kernel**；
- 再加上由**当前 hidden state 计算的动态修正**；
- 每 **16 个通道**共享一组修正参数。

![[specdec-dflash2-bench-qwen3p8-27b.png]]
![[specdec-dflash2-bench-muse-glimmer.png]]

> 三张表分别是 Qwen3.5-4B（MTP / DFlash / DSpark / DFlash 2，均值 4.54 → 4.92 → 5.49 → **5.97**）、Qwen3.8-27B（MTP / DSpark / DFlash 2，均值 4.28 / 3.62 / **4.80**）、Muse Glimmer（DFlash / DSpark / DFlash 2，均值 4.44 / 4.48 / **5.70**）。

## 三、数据匹配：不用模型，从历史文本里查

利用历史数据/模板，通过规则匹配的方式生成字符，然后用大模型进行校验，如 N-gram、suffix decoding。

### 3.1 N-gram

**gram 指代元组**。这是一种基于历史数据进行概率计算并获得预测结果的方式，核心思想是：**一个词出现的概率依赖于它前面的 N−1 个词**。

在推理中应用 N-gram 方法，一般步骤：

1. 确定**匹配长度**、**预测长度**；
2. 根据已有数据（prompt 或者历史数据）构建 N-gram 词表；
3. 用主模型验证结果，若满足则接受，反之亦然。

### 3.2 Suffix decoding（尾缀匹配）

根据输出数据来构造**后缀树**，匹配到合适的后缀后选择**得分最高**的值作为输出，得分的高低与**数据出现频率**相关。suffix decoding 涉及两个关键参数：**窗口大小 P**、**后缀节点数量 N**。结合下图示例（P=2, N=3），输入为「85485」，suffix decoding 匹配的头有两种：「5」和「8, 5」。

基本步骤：

1. 根据保存的**历史数据**，构造第一个后缀树；
2. 根据**当前输出**构造另一棵后缀树；
3. 找出两棵后缀树中满足要求的子树；
4. 对子树进行打分排序，挑选出分数最高的子树；
5. 用 LLM 验证子树的值是否满足要求，若满足则接受。

![[specdec-suffix-tree-draft-pipeline.png]]

> **这一类的定位**：draft 成本近乎为零，但只在**大量复读**的场景才有命中率（改代码、按模板抽取、RAG 长引用）。开放问答上基本白跑。好处是**不需要任何额外权重**，随时可开可关。

## 四、怎么选

| 场景 | 建议 | 理由 |
|---|---|---|
| 模型原厂带 MTP 头 | 直接用 MTP | 权重现成、和主模型一起训过，接受率最高 |
| 有训练资源、要通用加速 | EAGLE-3 / DFlash 系 | 接受率高，但要自己训 draft |
| 输出大量复读原文 | N-gram / suffix decoding | 零成本，无需权重 |
| 高并发在线服务 | **先掂量要不要开** | 投机采样吃的是「算力闲置」红利，大 batch 下 GPU 已接近喂饱，draft 反而和真实请求抢算力 |

> ⚠️ 存疑：这张表是我按前三节的机制归纳的选型建议，**你的原笔记只记了各方法的机制、没有写选型结论**。最后一行「高并发慎开」的方向应该稳（[[LLM分布式]] §8.3 有同样的推论），但**没有实测依据**，当作待验证的判断。
